## Using Docker

The application keeps the `hyperglass` service and configuration names. Set `RELEASE_TAG` to the published tag you select from the [releases page](https://github.com/hyperglass-community/hyperglass/releases). The migration release is 3.0.0. These steps apply to `v3.0.0-rc.2`. Ultraglass release numbers do not name community Hyperglass releases.

```shell copy
cd /opt/hyperglass
docker compose down
docker compose rm -f
git fetch --tags
git checkout "$RELEASE_TAG"
chown -R 10001:10001 /etc/hyperglass
docker compose pull
docker compose up -d
```

From 3.0.0 the container runs as UID `10001` instead of root. The `chown` gives it the configuration directory and the `.ui` and `static` directories that an older image left owned by root. Without it, the container stops with `Permission denied` and restarts in a loop. If `HYPERGLASS_APP_PATH` is set, change the owner of that directory instead. See [container user and file ownership](/installation/docker.mdx#container-user-and-file-ownership) for log directories and SSH keys.

If the `systemd` unit or `hyperglass.env` is still in `/etc/hyperglass`, move them as described in [Move the service and environment file out of the app directory](#move-the-service-and-environment-file-out-of-the-app-directory).

The Compose file pulls the published image for the checked-out release. It no longer builds the checkout. To run local source changes, add the build override:

```shell copy
docker compose -f compose.yaml -f compose.build.yaml up -d --build
```

## Manual installation

Update the checked-out release, reinstall the package in the virtual environment, then restart the service. Hyperglass rebuilds the UI at start when the version changes.

```shell copy
cd /opt/hyperglass
git fetch --tags
git checkout "$RELEASE_TAG"
. .venv/bin/activate
python -m pip install -e '.[ui]'
systemctl restart hyperglass
```

If the `systemd` unit or `hyperglass.env` is still in `/etc/hyperglass`, move them as described in [Move the service and environment file out of the app directory](#move-the-service-and-environment-file-out-of-the-app-directory).

## Move the service and environment file out of the app directory

Earlier installation guides put the `systemd` unit and its environment file in the app directory, as `/etc/hyperglass/hyperglass.service` and `/etc/hyperglass/hyperglass.env`, and linked the unit into `/etc/systemd/system`. `systemd` reads both files as root. With Docker, the container can write to that directory, so a compromised container could change them and have its own commands run as root on the host at the next restart. The sample units now read `/etc/default/hyperglass`, and the guides install the unit in `/etc/systemd/system`.

Move both files once, after checking out a release whose `.samples` units read `/etc/default/hyperglass`. The container could have changed the old files, so review them before you copy them. Use `hyperglass-manual.service` instead of `hyperglass-docker.service` for a manual installation. If you set `HYPERGLASS_APP_PATH`, replace `/etc/hyperglass` in the old file paths below with your app directory.

First stop the service and show the old files:

```shell copy
systemctl stop hyperglass
systemctl disable hyperglass
cat /etc/hyperglass/hyperglass.env
diff /opt/hyperglass/.samples/hyperglass-docker.service /etc/hyperglass/hyperglass.service
```

Check that the environment file sets only variables you put there. A `COMPOSE_FILE` you did not set, or one that names a file outside `/opt/hyperglass`, means the file was changed. The `diff` shows the new `EnvironmentFile` line and your own changes to the old unit. Any other difference, such as a changed `ExecStart`, means the unit was changed. If either file was changed, treat the host as compromised and do not continue.

Then copy the files out of the app directory and remove the old ones:

```shell copy
install -o root -g root -m 600 /etc/hyperglass/hyperglass.env /etc/default/hyperglass
rm -f /etc/systemd/system/hyperglass.service
cp /opt/hyperglass/.samples/hyperglass-docker.service /etc/systemd/system/hyperglass.service
rm /etc/hyperglass/hyperglass.service /etc/hyperglass/hyperglass.env
```

`install` copies the environment file with root as its owner. `mv` would keep the owner, and after `chown -R 10001:10001 /etc/hyperglass` that is the container user. `systemctl disable` may already have removed the link in `/etc/systemd/system`, so `rm -f` ignores a missing one. Apply the changes from the old unit that you want to keep to `/etc/systemd/system/hyperglass.service`, and check that `ls -l /etc/systemd/system/hyperglass.service` shows a regular file owned by root, not a link.

Then start the service from the new unit:

```shell copy
systemctl daemon-reload
systemctl enable hyperglass
systemctl start hyperglass
```

Until you move them, the old files keep working: an installed unit keeps its `EnvironmentFile` path. Only a unit copied from the new sample reads `/etc/default/hyperglass`, and `systemd` does not start it while that file is missing.

## Migrating from Hyperglass 2.0.4

Back up `config.yaml`, `devices.yaml` and `directives.yaml` before upgrading. The service and configuration names remain `hyperglass`. Validate the configuration with `hyperglass onboard check` before exposing the upgraded service.

Hyperglass 3.0.0 adds these changes:

- New built-in platforms: `aruba_aoscx`, `cumulus_linux`, `dell_force10`, `dell_os10`, `fortinet`, `hp_comware`, `ipinfusion_ocnos` and `paloalto_panos`. See [devices](/configuration/devices.mdx) for the `attrs` and VRF forms each platform uses.
- The `hyperglass onboard` command creates and tests device entries, checks feature settings, and scaffolds custom directives. See [device onboarding](/configuration/onboarding.mdx).
- Structured output requires `structured_output: true` on every supported device, including FRR, Juniper and Arista. Omitted, `null` and `false` settings return text.
- Custom VRF directives remain supported. Numeric VRFs normalize to strings; spaces and slashes remain invalid.
- Custom directives now quote substituted arguments on shell-backed platforms, including permissive rules. Review templates that depend on shell expansion or split one target into multiple arguments. Use explicit placeholders for separate arguments. Never pass visitor input to `eval` or `sh -c`. See [custom directive quoting](/configuration/directives.mdx).
- A custom directive whose id is a built-in directive's id, such as `__hyperglass_juniper_ping__`, stops startup with an error that names it. Such a directive replaced the built-in, so devices lost that query type, and no device could use it, since devices ignore ids that start with `__`. Give it a new id that doesn't start with `__`, list it in the device's `directives`, and leave the built-in out with `builtins: false` or a list of built-ins. See [Change a Built-in Command](/configuration/examples/add-your-own-command.mdx#change-a-built-in-command).
- Valid zero-route MikroTik results complete without repeated SSH sessions.
- Docker Compose pulls the published image and runs Valkey 8 as the `redis` service. It no longer builds the checkout; add `compose.build.yaml` for a source build. Existing `HYPERGLASS_REDIS_*` settings keep their meaning, and the bundled cache starts empty.
- The container runs as the unprivileged user `hyperglass` (UID and GID `10001`) instead of root. The host directory mounted at `/etc/hyperglass`, any mounted log directory and SSH key files must belong to that user. See [Using Docker](#using-docker).
- The `systemd` unit and its environment file move out of the app directory, to `/etc/systemd/system/hyperglass.service` and `/etc/default/hyperglass`. See [Move the service and environment file out of the app directory](#move-the-service-and-environment-file-out-of-the-app-directory).
- The automatic worker count follows CPU affinity and the container CPU quota, and stops at eight. Set `HYPERGLASS_WORKERS` to keep a higher count.
- Cisco IOS and NX-OS IPv6 BGP Route queries require a prefix no longer than `/127`.
- IP rules refuse link-local targets (IPv4 `169.254.0.0/16`, IPv6 `fe80::/10`) and IPv6 targets with a zone, such as `fe80::1%eth0`, including with a `0.0.0.0/0` or `::/0` rule and on built-in directives. To query link-local addresses from a custom directive, set `allow_link_local: true` on its IP rule. Zones are then accepted only on link-local host addresses. See [IP rules](/configuration/directives.mdx).
- In a custom directive with IP rules, a pattern rule or a rule without validation no longer accepts a zoned, loopback, unspecified, link-local or reserved IP target. Such a target needs an IP rule that contains it, with the matching `allow_*` option, placed before the other rule. See [IP rules](/configuration/directives.mdx).
- HTTP devices receive default HTTP configuration when the `http` block is omitted.
- Forwarding headers require a trusted proxy. An installation behind a reverse proxy must set `web.client_ip.trusted_proxies` to keep visitor addresses for My IP, the webhook `source` and the per-client limits. See [Client Address](/configuration/config/web-ui.mdx#client-address).
- `/api/dns` and `/api/aspath/enrich` are disabled by default. `web.dns_provider.name: server` enables server DNS, which asks Cloudflare's public resolver and returns public addresses only. `web.aspath_enrichment: true` enables the ASN name lookup in the AS path view.
- The default fonts, Nunito and Fira Code, ship with hyperglass, so visitors no longer fetch them from Google Fonts. Another font set in `web.theme.fonts` is still fetched from Google by visitors' browsers, as in 2.0.4, which shows Google their IP addresses. Set `web.theme.fonts.download: true` to have the server download and serve it. **Upgrading from a 3.0.0 release candidate:** the release candidates downloaded and served every configured font. With a non-default font, set `download: true` to keep that. See [fonts](/configuration/config/web-ui.mdx#fonts).
- Support bundles export metadata only. They no longer include free-form messages or exception values.
- The unused upstream BGP community input plugin is removed. Built-in directives check the syntax and range of community targets: a 32-bit number, standard `ASN16:VALUE16`, large `ASN32:VALUE32:VALUE32`, or extended `target:` or `origin:` followed by `ASN16:VALUE32`, `ASN32:VALUE16` or `IPv4:VALUE16`. Out-of-range values such as `70000:1` are refused before a command is sent. Well-known community names, such as `no-export`, are refused on every built-in directive, as before.
