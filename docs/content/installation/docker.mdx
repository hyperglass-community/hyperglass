## Deploy a published image

After `v3.0.0-rc.2` is published, download the Compose file and sample configuration without cloning the source repository:

```shell copy
mkdir -p /opt/hyperglass /etc/hyperglass
cd /opt/hyperglass
curl -fsSLo compose.yaml https://raw.githubusercontent.com/hyperglass-community/hyperglass/v3.0.0-rc.2/compose.yaml
curl -fsSLo /etc/hyperglass/devices.yaml https://raw.githubusercontent.com/hyperglass-community/hyperglass/v3.0.0-rc.2/.samples/sample_devices.yaml
chown -R 10001:10001 /etc/hyperglass
docker compose pull
docker compose up -d
```

The container runs as UID `10001`, so it must own `/etc/hyperglass`. See [container user and file ownership](#container-user-and-file-ownership).

The sample device returns fake output. Replace it with your devices after checking the page at `http://localhost:8001`. The first start builds the configuration-specific UI.

The Compose file uses `ghcr.io/hyperglass-community/hyperglass:3.0.0-rc.2` and Valkey 8. Set `HYPERGLASS_IMAGE` in `.env` to select another published version. A push to `main` whose run passes `CI gate` and the image scan is also published, for the pushed head commit only, as `sha-<commit>` (for example `ghcr.io/hyperglass-community/hyperglass:sha-<full commit SHA>`) for testing unreleased changes. These images are not releases: they never move `latest` and receive no support. The cache service remains named `redis`, and existing `HYPERGLASS_REDIS_*` settings keep their meaning. External Redis deployments remain supported. The cache is disposable; this change does not migrate an external Redis database.

## Verify a published image

{/* TODO: if #458 merges, `sha-` images from main are attested too. Say so here. */}

Release images carry a signed build provenance attestation and an SPDX SBOM attestation. Images published before attestations were introduced have none, so verification fails for them. Verify that an image was built by this repository's CI with the [GitHub CLI](https://cli.github.com/), replacing `<version>` with the image tag:

```shell copy
gh attestation verify oci://ghcr.io/hyperglass-community/hyperglass:<version> -R hyperglass-community/hyperglass
```

The output names the workflow and commit that built the image. To verify the SBOM and print it:

```shell copy
gh attestation verify oci://ghcr.io/hyperglass-community/hyperglass:<version> -R hyperglass-community/hyperglass \
    --predicate-type https://spdx.dev/Document/v2.3 \
    --format json --jq '.[].verificationResult.statement.predicate'
```

### Download Hyperglass

```shell copy
mkdir /etc/hyperglass
touch /etc/hyperglass/hyperglass.env
git clone https://github.com/hyperglass-community/hyperglass.git --depth=1 /opt/hyperglass
cd /opt/hyperglass
```

Clone into `/opt/hyperglass`. The sample `systemd` service runs `docker compose` from that directory. The service also reads `/etc/hyperglass/hyperglass.env`, and `systemd` does not start it if that file is missing.

<Callout type="info">Use `compose.build.yaml` with the main Compose file to build the `hyperglass:local` image. Version tags publish release images to GHCR after the required checks pass. Pushes to `main` publish only `sha-<commit>` images. Pull requests do not publish images.</Callout>

### Optional: Quickstart

Do this if you want to verify the Hyperglass page with a fake device before connecting real network devices.

```shell copy
cp /opt/hyperglass/.samples/sample_devices.yaml /etc/hyperglass/devices.yaml
chown -R 10001:10001 /etc/hyperglass
cd /opt/hyperglass
docker compose -f compose.yaml -f compose.build.yaml up --build
```

Open http://localhost:8001. The first start builds the UI, which takes a few minutes. Dependency layers are cached independently of application source changes.

### Create a `systemd` service

<Callout type="info">Before you create and start the Hyperglass service, verify whether you need to change any [environment variables](environment-variables.mdx).</Callout>

The service uses the published image by default. For a source build, set `COMPOSE_FILE=/opt/hyperglass/compose.yaml:/opt/hyperglass/compose.build.yaml` in `/etc/hyperglass/hyperglass.env` and build the local image first.

```shell copy
cp /opt/hyperglass/.samples/hyperglass-docker.service /etc/hyperglass/hyperglass.service
ln -s /etc/hyperglass/hyperglass.service /etc/systemd/system/hyperglass.service
systemctl daemon-reload
systemctl enable hyperglass
systemctl start hyperglass
```

## Container user and file ownership

The image runs Hyperglass as the unprivileged user `hyperglass`, with the fixed UID and GID `10001`. On first start, Hyperglass writes into `/etc/hyperglass`: the UI build workspace (`.ui`), the built UI and images (`static`) and user plugins (`plugins`). That directory must be writable by UID `10001`.

A host directory created with `mkdir` as root is owned by root, and the container exits with `Permission denied: '/etc/hyperglass/plugins'`. Give the directory to the container user before the first start, and again after upgrading from an image that ran as root, since that image left root-owned files behind:

```shell copy
sudo chown -R 10001:10001 /etc/hyperglass
```

The configuration files only need to be readable by UID `10001`.

- **Custom application path.** Compose mounts `HYPERGLASS_APP_PATH` from the host when it is set. Change the owner of that directory, not `/etc/hyperglass`.
- **Logs and query samples.** A host directory mounted for `logging.directory` or `logging.samples.path` must be writable by UID `10001`.
- **SSH keys.** A key file referenced by a credential's `key` must be readable by UID `10001`. A root-owned key with mode `0600` is not. Change its owner to `10001` and keep mode `0600`.

## Client addresses and host nginx

The default Compose setup runs Hyperglass and Valkey without a reverse proxy. Keep `web.client_ip.trusted_proxies: []` for direct access. Hyperglass ignores forwarding headers and uses the connecting address. My IP returns `null` for loopback or private addresses, so a local visit does not insert a Docker gateway address.

For nginx on the Docker host, restrict the published application port before trusting proxy headers. Add this to `.env` beside `compose.yaml`:

```dotenv
HYPERGLASS_BIND_ADDRESS=127.0.0.1
```

Keep `HYPERGLASS_HOST=0.0.0.0` inside the container. `HYPERGLASS_BIND_ADDRESS` controls the host's published port; it does not change the container listener. Recreate the service to apply the port binding:

```shell
docker compose up -d hyperglass
docker compose port hyperglass 8001
```

For the default port, the second command must show `127.0.0.1:8001`. Point nginx at `http://127.0.0.1:8001`: the supplied `.samples/hyperglass.nginx` uses `http://[::1]:8001` for an installation without Docker, so change its `proxy_pass` line. The sample overwrites `X-Real-IP` and `X-Forwarded-For` with `$remote_addr`.

On Linux Docker bridge networking, Hyperglass sees host nginx through the bridge gateway, not `127.0.0.1`. Find that gateway:

```shell
docker inspect "$(docker compose ps -q hyperglass)" --format '{{range .NetworkSettings.Networks}}{{println .Gateway}}{{end}}'
```

Merge the following into `/etc/hyperglass/config.yaml`, replacing `172.18.0.1/32` with that exact gateway address and `/32`:

```yaml
web:
    my_ip: server
    client_ip:
        header: X-Real-IP
        trusted_proxies:
            - 172.18.0.1/32
```

Do not trust the whole Docker subnet or all private networks. Restart Hyperglass after changing `config.yaml`, then reload nginx. Recheck the gateway if Compose recreates its network. For nginx in another container, trust that proxy container's address instead and keep the application port inaccessible to visitors. A CDN before nginx needs its own explicit trust configuration in nginx.

Verify from a remote client through nginx. `/api/myip?family=4` must return the visitor's public IPv4 address. Supplying a forged `X-Real-IP` header must not change that result. Webhook `source` uses the same trusted address. Direct access to the host's port 8001 must be unavailable remotely.

Docker Desktop or another network layer can replace the visitor address before Hyperglass receives it. Do not trust forwarding headers from that gateway when visitors can connect directly. `web.my_ip: external` enables browser-side public IP lookup, but webhook attribution still requires a correctly configured proxy.
