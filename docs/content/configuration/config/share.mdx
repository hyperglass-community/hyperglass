## Share Snapshots

A visitor can copy a result from the query cache into a snapshot: a copy kept on the server that anyone with its ID can read until it expires, even after the query's cache entry has expired or the query has been run again. It is off by default.

<Callout type="warning">
    Anyone who can run a query can snapshot any result that is currently in the cache, including results other visitors queried, and anyone with a snapshot's ID can read it. A snapshot keeps the result, its target and its query variables until it expires. Keep a directive's results out of snapshots with [`retain: false`](/configuration/directives).
</Callout>

| Parameter                       | Type    | Default  | Description |
| :------------------------------ | :------ | :------- | :---------- |
| `share.enable`                  | Boolean | `false`  | Register `POST /api/share`, `GET /api/share/{id}` and `DELETE /api/share/{id}`, and show a [Share button](#the-share-button) on results. With `false`, none of them exist. Sent to the UI. |
| `share.timeout`                 | Integer | `2592000` | Seconds a snapshot is kept when the request doesn't choose (no `expiresIn`). Must be one of `timeout_choices`. Reading a snapshot doesn't extend it. |
| `share.max_timeout`             | Integer | `7776000` | The longest a visitor can choose, from `60` to `31536000` (1 year). `timeout_choices` above it are dropped. Lowering it doesn't shorten existing snapshots; delete them with `hyperglass share delete` or `hyperglass share clear`. Set below `timeout`, Hyperglass doesn't start (even with sharing off) until `timeout` is one of the remaining choices. |
| `share.timeout_choices`         | List of Integers | `[604800, 2592000, 7776000]` | Times, in seconds, a visitor can choose to keep a snapshot for: 7, 30 and 90 days. Sorted and without duplicates once validated. With `timeout`, sent to the UI for its choice. |
| `share.max_entries`             | Integer | `1000`   | Live snapshots from all clients together. When full, a new share gets HTTP 503. Existing snapshots are never deleted to make room. |
| `share.max_size`                | Integer | `262144` | Bytes of one stored snapshot. A larger result gets HTTP 413. |
| `share.quota.client_limit`      | Integer | `10`     | Shares one client can create per window: an IPv4 address or an IPv6 /64. |
| `share.quota.global_limit`      | Integer | `100`    | Shares all clients together can create per window. |
| `share.quota.window`            | Integer | `3600`   | Length of the share counting window, in seconds, up to 2592000. Also sent as `Retry-After`. |
| `share.read_quota.client_limit` | Integer | `60`     | Snapshot reads and delete requests per window from one client. |
| `share.read_quota.global_limit` | Integer | `1200`   | Snapshot reads and delete requests per window from all clients together. |
| `share.read_quota.window`       | Integer | `60`     | Length of the read counting window, in seconds, up to 2592000. Also sent as `Retry-After`. |

### Example

```yaml filename="config.yaml"
share:
    enable: true
    timeout: 2592000
    max_timeout: 7776000
    timeout_choices: [604800, 2592000, 7776000]
    max_entries: 1000
    max_size: 262144
    quota:
        client_limit: 10
        global_limit: 100
        window: 3600
```

### Storage

Snapshots are kept in Redis under `hyperglass.share:`, outside the state Hyperglass deletes when it starts, so they survive a restart of Hyperglass. Each snapshot is stored once, as JSON, with its expiry set; a sorted set of IDs counts the live ones.

- **Worst case:** `max_entries × max_size`, 256 MiB with the defaults, plus a few hundred bytes per snapshot. Size Redis for it, or lower either value.
- **Snapshot size:** a structured BGP result takes roughly 350 to 500 bytes per route, so the default `max_size` holds a result of about 500 routes. Larger results get HTTP 413 with [`messages.share_too_large`](/configuration/config/messages).
- **Lifetime:** a snapshot lives as long as the visitor chose, up to `max_timeout` (90 days by default). The longer snapshots live, the more a restart of Redis without persistence loses, and the longer a full store stays full.
- **Restarts of Redis:** snapshots survive a restart of Redis only if Redis persists its data (RDB snapshots or an append-only file) to a volume. The shipped `compose.yaml` runs Redis (Valkey) without a volume, so restarting that container deletes every snapshot. Add a volume for `/data` to keep them.
- **Memory limits:** if Redis has a `maxmemory` limit, use the `noeviction` policy or a `volatile-*` policy; `allkeys-*` policies can also delete Hyperglass's configuration state.
  - With `noeviction`, a full Redis refuses writes. New shares then get HTTP 503 with `messages.share_unavailable`; existing snapshots can still be read and deleted, without being counted against `read_quota`. Queries are affected too: a query that is not in the cache fails with HTTP 500 when its result can't be written to the cache, and with [`query_limit`](/configuration/config/query-limit) enabled every query does, because its counter can't be written.
  - Every snapshot has an expiry, so a `volatile-*` policy can delete snapshots before they expire. Their IDs stay in the index until their expiry time: `hyperglass share list` shows them as `(not_found)`, and they count toward `max_entries` until the store is full, when a new share removes the IDs whose snapshot is gone before it counts again.
- **Several instances** sharing one Redis database share their snapshots too; give each instance its own `HYPERGLASS_REDIS_DB`.

### API

All three routes need `share.enable: true`. Their error bodies have the same shape as other errors, with the text from [`messages`](/configuration/config/messages). While Redis is unreachable, each answers HTTP 503.

#### `POST /api/share`

```json
{ "queryId": "hyperglass.query.<64 hex characters>", "expiresIn": 2592000, "timestamp": "2026-11-23 08:00:00" }
```

`expiresIn` is optional: absent or `null`, the snapshot is kept for `timeout` seconds. Otherwise it must be one of `timeout_choices` (after the `max_timeout` cap), as an integer.

`timestamp` is optional: the `timestamp` of the same `POST /api/query` response, as a string of 1 to 64 characters. `queryId` names the query's cache entry, not one result: once the query has run again (refreshed with `force`, or after its cache entry expired), the entry holds the newer result. With `timestamp`, the server shares only the result the device produced at that time, and answers 404 when the cache holds another. The UI always sends it, so a result opened from the query history is never shared as a newer result.

`queryId` is the `id` of a `POST /api/query` response. The result must still be in the query cache: the server copies the result, its query (location, query type ID and name, validated target, variables), its labels, format, time and runtime from the cache entry, never from the request.

| Status | Meaning |
| :----- | :------ |
| 201    | Created. The body is `{"id": …, "expiresAt": …, "deleteToken": …}`. |
| 200    | This client already shared this cached result: the same `id` and `expiresAt`, whatever `expiresIn` says, and a new `deleteToken`. The previous token no longer works. A result refreshed with `force`, or run again after its cache entry expired, gets a new ID. |
| 400    | The body is not `{"queryId": …}` with a query ID, `timestamp` is not a string of 1 to 64 characters, or `expiresIn` is not one of `timeout_choices` (with `messages.share_invalid_expiry`). |
| 413    | The body is larger than 1024 bytes. |
| 415    | The body is not sent as `application/json`. A page on another site can make a browser send a form or `text/plain` post without asking, which would use up its visitor's quota; a JSON post needs a CORS preflight, which only the origins in `cors_origins` pass. |
| 403    | The result's directive has `retain: false`. |
| 404    | The result is no longer cached, or the cache holds a result with another `timestamp` than the one sent. |
| 409    | The result's enrichment is still running. |
| 413    | The snapshot would be larger than `max_size`. |
| 429    | The client, or all clients together, created `quota` shares in this window. `Retry-After` is `quota.window`. |
| 503    | `max_entries` snapshots exist, Redis is full (`maxmemory` with `noeviction`), or Redis is unreachable. |

Every response of the three routes, errors included, has `Cache-Control: no-store`: a create response carries the delete token, and any answer can change with the next request.

The share ID is 16 random bytes in hex. The delete token is 32 random bytes in URL-safe base64; only its SHA-256 hash is stored, and it is never logged. Keep it to delete the snapshot later.

#### `GET /api/share/{id}`

Returns the snapshot: `id`, `version`, `createdAt`, `expiresAt` and `results`, a list with one result for now. Each result has `query`, `labels`, `output`, `format`, `timestamp` and `runtime`. The response has `Cache-Control: no-store` and `X-Robots-Tag: noindex`. Reading a snapshot doesn't extend its expiry.

The stored snapshot is checked against its format before it is returned. A snapshot that doesn't match, for example one changed by hand in Redis, gets HTTP 404 and is logged as an error. One stored in a `version` this release doesn't read, for example after a downgrade, gets HTTP 422 with `messages.share_unsupported`. A snapshot whose location or query type has since been removed from the configuration, or whose directive now has `retain: false`, gets HTTP 404; it is kept until it expires, so setting `retain: true` again serves it.

Reads are counted per client and globally against `read_quota`; over it, HTTP 429 with `Retry-After`. An ID that isn't 32 hexadecimal characters gets HTTP 404 without a lookup.

#### `DELETE /api/share/{id}`

Send the delete token in the `X-Delete-Token` header, never in the URL. HTTP 204 when the snapshot is deleted. A wrong or missing token gets the same HTTP 404 as an ID that doesn't exist, so the answer doesn't tell whether an ID exists. Delete requests count against `read_quota`, like reads.

If the client's existing share of a result can no longer be read (for example, changed by hand), a new share request replaces it with a new snapshot and ID.

### The Shared Result Page

A share link is the landing page with the share ID in its address: `https://<your hyperglass>/?share=<id>`. It works with the static UI export and wherever the UI is served from. The page shows the shared result in place of the form, read-only: the query type, target, location and output, the time the device ran the query and when the link expires, both in the viewer's time zone. Output is shown as text, as live results are; reverse DNS names, AS paths and communities from the snapshot are never read as markup. The output can be copied, and the AS path of structured output (a BGP table or a traceroute) can be opened, without looking up ASN names. There is no requery, polling or other request: the page makes only the one `GET /api/share/{id}` request, without following redirects, and only for an ID of 32 hexadecimal characters (any other shows "not found" without a request). Structured output missing a field the tables read, or with a value of the wrong type, shows `web.text.share_error` instead of the result.

- **Run this query** fills the form with the shared query, as a [link to a filled-in form](/user-guide#link-to-a-filled-in-form) does: the visitor submits it, so a required greeting still applies, and values the configuration no longer has are left out. **New query** shows an empty form. Both remove `share` from the address.
- Any other form parameter in a share link (`location`, `type`, `target`, `var.*`) is ignored and removed from the address, so a link can't pair a real snapshot with a form someone else filled in.
- A link that doesn't exist, has expired or was deleted shows `messages.share_not_found`; a snapshot saved in a format this version can't read (HTTP 422) shows `messages.share_unsupported`; a rate-limited read shows `messages.rate_limited`; any other failure shows `web.text.share_error`. The page's own text is in [`web.text`](/configuration/config/complete-config#shared-result-text): `share_title`, `share_loading`, `share_error`, `share_result_time`, `share_expires`, `share_run_query` and `share_new_query`.
- While a share is shown, the page has `<meta name="robots" content="noindex">`. Every page Hyperglass serves from the UI has `Referrer-Policy: same-origin`, so browsers don't send its address, with the share ID, to other sites the page loads from or links to (such as the ASN links to bgp.tools). The page also carries `<meta name="referrer" content="same-origin">` before anything it loads, which covers a UI served by something other than Hyperglass; setting the header there too is still recommended.
- The page never reads or shows a delete token.

With `share.enable: false`, a share link shows "not found".

During UI development (`next dev`), `/api/share/<id>` is proxied to `HYPERGLASS_URL`, as `/api/query` is.

### The Share Button

With sharing on, each successful result in the results view has a Share button next to copy and requery. It is not shown for an error, while the result's AS path enrichment is still running (the server would answer 409), or when the location's directive has `retain: false`. The UI checks `retain` as the query history does, which is at least as strict as the server: on a device with two directives of the same name and one of them `retain: false`, queried with another vendor's directive ID, the button is hidden although the server would share the result of the directive it runs.

The button opens a popover with a **Keep for** choice of `timeout_choices` (with `timeout` selected) and a button that creates the share with that `expiresIn`. Once created, the popover shows the link (the page's own origin and path, with `?share=<id>`) in a read-only field, a button to copy it, its expiry in the viewer's time zone, a notice that anyone with the link can see the result including its target, and a button that deletes it.

- The delete token is kept in the page's memory, with the link, so the popover shows the link again until the page is closed or reloaded (`web.text.share_delete_scope` says so). It is never put in a URL, the link, web storage or a log, and is sent only in the `X-Delete-Token` header of `DELETE /api/share/{id}`. Deleting the link forgets it; an expired link is forgotten at its expiry, announced with `web.text.share_link_expired` when the popover is open. After a reload, sharing the same cached result again returns the same link with a new token.
- Links are kept per query and device. When the query runs again (a forced refresh, or after its cache expired), the new result has no link yet and can get its own, and the links of the earlier results stay in the popover, labelled `web.text.share_earlier_link`, each with its copy and delete buttons. A link created while the query was running again is filed under the result it was created from.
- A delete answered with 404 is followed by one `GET /api/share/{id}`, without the token. If the share is gone, the link is forgotten and `messages.share_not_found` is shown. If it still exists, its token was replaced: the same client (the same IPv4 address or IPv6 /64) shared the result again from another page or browser. The link is kept, its token is dropped, and `web.text.share_delete_rotated` replaces the delete button. Such a link can still be deleted from the page that shared it last, or with `hyperglass share delete`.
- A link's remaining lifetime is counted from the server's answer: its `expiresAt` less the response's `Date` header (or, without one, the chosen time from the request). A browser whose clock is off from the server's doesn't drop a live link. The expiry shown is the server's `expiresAt`, in the viewer's time zone.
- Refused requests show the matching message, never the response's text: `messages.share_result_expired` (404), `share_pending` (409), `share_not_allowed` (403), `share_too_large` (413), `share_invalid_expiry` (400), `share_unavailable` (503), `rate_limited` (429), `share_not_found` (a link that is gone, see above), and `messages.general` for anything else. Nothing is retried on its own.
- The popover's text is in [`web.text`](/configuration/config/complete-config#share-button-text). Each time to keep the link is shown in the largest unit it is a whole number of: days (`share_day`, `share_days`), hours (`share_hour`, `share_hours`) or minutes (`share_minute`, `share_minutes`). Each unit has one singular and one plural form, which suits languages with two forms; a language with more plural forms can only approximate them.

During UI development (`next dev`), `POST /api/share` is proxied to `HYPERGLASS_URL` too.

### Operator Commands

```shell
hyperglass share list         # ID, times, location, query type and target of each live snapshot
hyperglass share delete <id>  # delete one snapshot, without its token
hyperglass share clear        # delete every snapshot (asks first; --yes skips the question)
```

`hyperglass share delete` accepts only share IDs (32 hexadecimal characters), so it can't delete the index or another key. `hyperglass clear-cache` does not delete snapshots.

### Limits on Abuse

Creating shares is cheap to refuse but can be used to deny sharing to others:

- Every create request that passes validation counts toward `quota`, including requests refused with 403, 404, 409 or 413. A client can use up its own quota, and clients with many addresses or /64s can use up `quota.global_limit` for a window.
- A full store (`max_entries`) refuses new shares until snapshots expire, which can take up to `max_timeout` (90 days by default) if the store was filled with the longest choice. With the defaults, filling it takes at least 10 windows of the global quota (10 hours). Lower `max_timeout`, or remove snapshots with `hyperglass share delete <id>` or `hyperglass share clear`.
- `hyperglass_share_requests_total` shows these as `rate_limited` and `full` results.

### How Clients Are Identified

Quotas count clients as [Query Rate Limit](/configuration/config/query-limit#how-clients-are-identified) does: by address, with IPv6 per /64, read through `web.client_ip` behind trusted proxies. The client identity is hashed before it is stored or logged. It decides whether a share request gets an existing ID: two visitors behind one IPv4 address or one IPv6 /64 are one client, so the second gets the first's ID and a new token for it. The identity is not stored in the snapshot.

### Metrics

With [metrics](/configuration/config/monitoring) enabled, `hyperglass_share_requests_total` counts share requests by `operation` and `result`.
