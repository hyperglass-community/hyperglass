## Cache

Hyperglass caches query responses in Redis, so a repeated query does not reach the device again until the cache entry expires.

| Parameter         | Type    | Default Value | Description                                                                     |
| :---------------- | :------ | :------------ | :------------------------------------------------------------------------------ |
| `cache.timeout`   | Number  | 120           | Number of seconds for which to cache device responses. Each cache hit restarts the timeout, so a query repeated within the timeout keeps its cached response. The UI countdown for cached results uses the same value. |
| `cache.show_text` | Boolean | `true`        | If `true`, the UI shows a cache icon and countdown on cached results. |
| `cache.refresh.enable` | Boolean | `false` | If `true`, a query sent with `force` can run a cached query on the device again. See [Forced refresh](#forced-refresh). |
| `cache.refresh.min_interval` | Number | 30 | Minimum seconds between runs of one query through `force`. Must be greater than 0 and less than `cache.timeout` when `cache.refresh.enable` is `true`. |

### Example with Defaults

```yaml filename="config.yaml"
cache:
    timeout: 120
    show_text: true
    refresh:
        enable: false
        min_interval: 30
```

### Forced refresh

With `cache.refresh.enable: true`, a query sent to `POST /api/query` with `"force": true` skips its cached result, runs on the device again and replaces the cache entry. `force` is not part of the cache key, so the forced query and the same query without it share one entry. With `cache.refresh.enable: false`, the default, `force` is ignored. It must be a boolean either way: any other value is rejected with HTTP 400.

`force` needs no authentication, so the server bounds forced runs for each query (location, query type, target and variables), whoever sends them:

- If the query ran less than `cache.refresh.min_interval` seconds ago, forced or not, the server answers from the cache.
- Only one forced run of a query happens at a time, across all workers. A forced query that arrives while another runs is answered from the cache. This relies on Redis keeping the run's lease key: if Redis evicts it under `maxmemory` pressure, a second forced run can start. The lease has an expiry, so `volatile-*` policies can evict it too; give Redis enough memory, or use `noeviction`, if that matters.
- After a forced run ends, whether it succeeded or failed, the next forced run of that query waits `cache.refresh.min_interval` seconds. Errors are not cached, so this also keeps a failing device from being queried again at once.
- A failed forced run returns the device's error, like any failed query, and keeps the previous cached result for the next request.

A query reaches the device through `force` at most once per `cache.refresh.min_interval`, plus the time the run takes. A query with no cached result runs as usual, with or without `force`.

If a worker stops in the middle of a forced run, its lease blocks forced runs of that query until the lease expires, `request_timeout` plus 5 seconds after the run started. Meanwhile `refresh_in` reports `min_interval`, and forced queries are answered from the cache.

Enabling forced refresh raises how often anyone can make a device run a given query: without it, a cached query runs at most once per `cache.timeout`; with it, once per `cache.refresh.min_interval` (four times as often with the defaults). For a query type whose target is free text, a visitor can already reach the device at any rate by changing the target. For query types with a fixed list of targets, or no target, forced refresh is what raises the rate. Choose `min_interval` with that in mind.

Every successful `/api/query` response includes `refresh_in`: the number of seconds until a forced query for the same result would run. `0` means now, and `null` means forced refresh is disabled. While another request's forced run is in progress, it is `min_interval`; a forced query sent sooner is answered from the cache with an updated value. Error responses do not include it, so a client learns the cooldown that follows a failed run from its next response. A response answered from the cache has `cached: true`.

With the default `cache.timeout` of 120 and `min_interval` of 30, a result can be refreshed from 30 seconds after it ran until it expires. After it expires, any request runs the query again.
